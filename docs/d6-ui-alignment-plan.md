## 一、登录改为读 POS 服务

### 1.1 现状问题

| 项 | 现状 | 问题 |
|---|---|---|
| 账号来源 | 主进程本地 `~/.nova/users.json`（scrypt 自管） | 账号不在 POS 服务里，与门店员工表脱节 |
| 身份可信度 | 渲染层登录后，主进程用自造载荷调 `POST /auth/token` | 角色由客户端自述，越权风险 |
| 员工表 | `User` 表仅 `id/avatar/name/password/email/status/extra` | 无 `role`、无「姓名」、`name` 无唯一约束、`password` 明文 |
| 登录接口 | `POST /user/login` 挂在 `app.use(internalAuth)` 之后 | 未登录拿不到 JWT，登录接口本身不可达 |

### 1.2 目标流程

```
渲染层 登录(用户名+密码)
  → 主进程 POST /user/login            （服务端校验 User 表，返回 id/name/realName/role，不含 password）
  → 主进程 POST /auth/token            （用真实 id/name/role 换 12h JWT）
  → 业务请求 Authorization: Bearer
```

- 删除 `~/.nova/users.json` 与本地 scrypt 逻辑；账号唯一来源是 POS `User` 表。
- `session.json` 只保留会话态（`userId / name / role / remember`），不再存任何凭据。
- 注册、修改密码同样走 POS；导购员下拉改用 `GET /user/list`（仅管理员）。

### 1.3 需要的服务端改动

| # | 改动 | 说明 |
|---|---|---|
| 1 | `/user/login`、`/user/register` 提到 `app.use(internalAuth)` 之前 | 公开接口，仅校验内部令牌，不要求 JWT |
| 2 | `userLogin` 返回值剔除 `password`，并返回 `role`、`realName` | 与 `/user/list` 口径一致 |
| 3 | `status !== 'normal'` 时拒绝登录 | 复用现有 `status` 字段做停用 |
| 4 | 密码改为 `scrypt$<salt>$<hash>`；历史明文首次登录成功后自动升级为哈希 | 老库现有密码是明文（默认 `123456`），必须平滑过渡 |
| 5 | 新增 `POST /user/changePassword`（本人改密，需校验旧密码） | 现有 `/user/update` 是管理员接口，导购员无法自助改密 |
| 6 | `createUser` 支持写 `realName`，默认 `role='clerk'` | 对齐新桌面端注册表单 |

### 1.4 数据表修改 SQL

服务端未开启 `sync({ alter: true })`，改表需手工执行。按顺序跑：

```sql
-- 0) 备份（务必先做）
CREATE TABLE `User_backup_20261027` AS SELECT * FROM `User`;

-- 1) 角色列：admin 管理员 / clerk 导购员
ALTER TABLE `User`
  ADD COLUMN `role` VARCHAR(16) NOT NULL DEFAULT 'clerk'
  COMMENT '角色：admin 管理员 / clerk 导购员' AFTER `password`;

-- 2) 姓名列：对齐注册表单的「姓名」
ALTER TABLE `User`
  ADD COLUMN `realName` VARCHAR(32) NULL COMMENT '姓名' AFTER `name`;

-- 3) 用户名唯一（先查重复，有重复先人工处理再建索引）
SELECT `name`, COUNT(*) AS c FROM `User` GROUP BY `name` HAVING c > 1;
ALTER TABLE `User` ADD UNIQUE KEY `uk_user_name` (`name`);

-- 4) 密码列扩宽，容纳 scrypt 哈希（历史明文保持原样，登录成功后由服务端自动升级）
ALTER TABLE `User`
  MODIFY COLUMN `password` VARCHAR(255) NOT NULL DEFAULT '123456'
  COMMENT '密码：scrypt$salt$hash，或历史明文';

-- 5) 状态兜底成 normal
UPDATE `User` SET `status` = 'normal' WHERE `status` IS NULL OR `status` = '';

-- 6) 指定门店管理员（把 <管理员用户名> 换成实际账号，可执行多遍）
UPDATE `User` SET `role` = 'admin' WHERE `name` = '<管理员用户名>';
```

执行后重启 POS 服务。若 `User` 表数据量小，第 3 步也可直接在图形化工具里先看重复行。

**无需 SQL 的项**：老账号的明文密码不用批量改写，服务端在首次登录校验通过后自动落成 `scrypt$` 哈希。

### 1.5 渲染层影响

- 登录页保留「用户名 / 密码」；注册页保留「用户名 / 姓名 / 密码 / 确认密码」，`姓名` 落到 `realName`。
- 登录失败文案改为服务端返回（如「用户名或密码错误」「账号已停用」）。
- 「忘记密码」当前是 `请联系管理员重置密码` 提示，保持。

## 三、需要你确认的决策点

1. **注册入口**：老系统允许自助注册；现在 `/user/register` 被列为管理员接口。是否改为公开自助注册（默认 `clerk`）？
