# 数据页指标卡「较上期」环比方案

> 适用范围：桌面端数据中心顶部 6 张指标卡。
> 流程图：[diagrams/06-cards-delta-flow.html](./diagrams/06-cards-delta-flow.html)

## 1. 目标

指标卡除展示当期绝对值外，再给出一行「较上期」对比，让店长一眼判断这 30 天是涨还是跌，不必自己翻两个日期区间做心算。

口径与订单页顶部的 5 张卡片完全一致，避免同一个概念在两个页面算出两个数。

## 2. 口径定义

| 项 | 规则 |
|---|---|
| 上一区间 | 与当前区间**等长**、**紧邻**、位于当前区间之前 |
| 计算方式 | 当前区间首日往前推 1 天 = 上一区间末日；再往前推 `days - 1` 天 = 上一区间首日 |
| 示例 | 当前 10/01–10/07（7 天）→ 上一期 09/24–09/30 |
| 单日区间 | 当前只选 1 天时，上一期就是「前一天」，等价于日环比 |
| 筛选口径 | 隐藏订单开关 `showStatus`、导购、支付方式等条件原样带入两次请求 |

## 3. 数据链路

1. 页面持有当前区间 `[start, end]`。
2. `previousRange(start, end)` 算出 `[pStart, pEnd]`。
3. `Promise.all` 并发两次 `POST /data/getCoreData`：当前区间 + 上一区间，两者参数除区间外完全相同。
4. `toSummary()` 把两次响应各自归一为 6 项指标。
5. `buildDelta(当期, 上期)` 得到文案与色调。
6. `StatCard` 的 `delta` 属性渲染成卡片底部那一行小字。

后端**没有**单独的环比接口，也不在服务端做时间窗推算——服务端只负责「给定区间算事实数」，时间窗比较属于展示层逻辑，前端算更灵活、也不增加接口面。

## 4. 计算规则

```ts
percent = (current - previous) / previous * 100
```

- 上一期为 `0`：显示 `— 较上期`（灰），不做除法，避免 ∞ 或 100% 的假象。
- 正增长：`+x.x% 较上期`，绿色；下降：`-x.x% 较上期`，红色。
- 保留 1 位小数。

## 5. 参与范围

| 指标卡 | 环比 | 原因 |
|---|---|---|
| 订单金额(CNY) | ✅ | 区间内的流水，随时间窗变化 |
| 余额消耗 | ✅ | 区间内余额扣减，随时间窗变化 |
| 订单数量 | ✅ | 区间内成交单量 |
| 售出商品 | ✅ | 区间内售出件数 |
| 商品库存 | ❌ | 当前时点的库存总量，不受 `dateRange` 影响 |
| 会员余额(CNY) | ❌ | 当前时点的会员余额合计，不受 `dateRange` 影响 |

后两项是**快照型**指标：服务端 `getCoreData` 无论传什么区间都返回同一数字，硬算会恒定显示 `+0.0%`，属于误导，因此不挂环比。若后续要给出「库存/会员余额的区间变化」，需要服务端新增「区间末时点回溯」口径，属于独立需求。

| 位置 | 职责 |

## 7. 边界与约定

- **切换区间**：区间变化即触发查询，当前指标与上一期指标在同一次响应中返回，不会出现卡片和环比不同步。
- **隐藏订单开关**：`showStatus` 同时进入两次请求；切换开关整页刷新后，环比按隐藏口径重算，不会混口径。
- **请求成本**：每次查询从 3 个请求增加到 4 个（多一次 `getCoreData`），并发执行，不增加首屏等待的串行段。
- **不做缓存**：上一期结果不落盘，避免历史数据变更后对比值陈旧。

## 8. 验证方式

1. 数据中心默认近 30 天，四张卡片底部出现「±x.x% 较上期」。
2. 把区间改成 10/01–10/07，另一环境查 09/24–09/30 的绝对值，手算百分比应一致。
3. 上一期无成交的区间（如选一个刚开业的日子），应显示「— 较上期」而非 `+100%`。
4. 切换隐藏订单开关后，被隐藏订单同时从当期与上期扣除，环比仍为同口径比较。
